TEXNIK TOPSHIRIQ (TZ)
Universal Business Management System — UBMS
Versiya: 2.0 (Detallashtirilgan) — asl v1.0 hujjat asosida kengaytirilgan
Platforma: Web + Desktop (Tauri 2)   |   Model: Multi-tenant SaaS
Yo'nalish: Restoran, do'kon, kafe, sartaroshxona va boshqa kichik/o'rta bizneslarni boshqarish
Ushbu hujjat maqsadi: dasturchi jamoasi yoki AI coding agent (masalan Antigravity) uchun UBMS loyihasining funksional, texnik, ma'lumotlar bazasi va API darajasidagi barcha talablarini aniq, bir xil talqin qilinadigan tarzda tavsiflash. Har bir modul: (a) maqsad, (b) ma'lumot maydonlari va validatsiya, (c) holatlar (status) mashinasi, (d) chegaraviy holatlar (edge cases), (e) ruxsatlar bo'yicha yozilgan.
0. Umumiy yozuv qoidalari va atamalar
Tenant — bitta biznes (businesses jadvalidagi bitta yozuv). Har bir so'rov tenant kontekstida ishlaydi.
Branch (filial) — tenant ichidagi jismoniy nuqta. Ko'p ma'lumotlar branch darajasida izolyatsiya qilinadi.
RBAC — Role-Based Access Control: role → permission[] → user.
Soft delete — status='archived'/'inactive' orqali, jismoniy DELETE faqat audit_logs va inventory_transactions kabi tarixiy jadvallarda taqiqlanadi.
Pul miqdorlari — barcha narxlar DECIMAL(14,2), floating-point ishlatilmaydi.
Barcha timestamp'lar — UTC da saqlanadi, frontend business.timezone bo'yicha konvertatsiya qiladi.
API xato formati — quyidagi bo'lim 27.4 da standartlashtirilgan.
1. Loyihaning maqsadi
UBMS — turli tur bizneslarni (do'kon, restoran, kafe, sartaroshxona, konditer, dorixona, xizmat ko'rsatish) bitta platformadan, bitta Core arxitektura ustida boshqarish imkonini beruvchi universal, multi-tenant SaaS tizim.
1.1 Muvaffaqiyat mezonlari (Success metrics)
Yangi biznes turi qo'shilganda Core kodga tegmasdan, faqat yangi modul qo'shish orqali amalga oshirilishi.
Bitta tenant ma'lumotlari boshqa tenantga hech qanday sharoitda (shu jumladan API xatosi orqali ham) ko'rinmasligi — 0 ta cross-tenant leak.
MVP: oddiy do'kon real vaqt rejimida to'liq ishlashi (login dan hisobotgacha).
POS tranzaksiyasi o'rtacha 2 soniyadan kam vaqtda yakunlanishi (checkout → chek chiqishi).
1.2 Loyiha doirasidan tashqarida (Out of scope, v1)
To'liq buxgalteriya/soliq hisoboti (faqat asosiy Finance moduli bilan cheklanadi).
Native mobil ilova (faqat responsive web, keyinchalik V3 da alohida).
Marketplace/e-commerce vitrina (faqat ichki boshqaruv tizimi).

3. Authentication
3.1 Ro'yxatdan o'tish (Register)
Maydonlar: full_name (majburiy, 2–150 belgi), phone (majburiy, E.164, UNIQUE), email (ixtiyoriy, UNIQUE), password (majburiy, min 8 belgi, kamida 1 harf + 1 raqam).
Telefon raqami SMS orqali tasdiqlanadi (OTP, 6 xonali kod, 5 daqiqa amal qiladi, 3 marta noto'g'ri urinishdan keyin 15 daqiqa bloklash).
Parol bcrypt (cost=12) yoki argon2id bilan hash qilinadi, hech qachon plaintext saqlanmaydi/log qilinmaydi.
Muvaffaqiyatli ro'yxatdan o'tishdan so'ng foydalanuvchi avtomatik login qilinadi va Business Onboarding (bo'lim 4) ga yo'naltiriladi.
3.2 Login
Kirish: (email YOKI phone) + password. Muvaffaqiyatsiz urinish soni user bo'yicha kuzatiladi: 5 ta ketma-ket noto'g'ri urinishdan keyin akkaunt 30 daqiqaga vaqtinchalik bloklanadi (status='pending' emas, alohida rate-limit lock).
Muvaffaqiyatli login natijasi:
access_token (JWT, 15 daqiqa amal qiladi, payload: user_id, business_id (agar tanlangan bo'lsa), role_id).
refresh_token (30 kun, faqat httpOnly secure cookie yoki secure storage'da, DB'da hash holida saqlanadi — rotatsiya bilan).
Agar user bir nechta bizneste ishlasa — biznes tanlash ekrani ko'rsatiladi (business_users bo'yicha).
3.3 Forgot password
Telefon/email orqali OTP yuboriladi → tasdiqlangach reset_token (10 daqiqa amal qiladi) beriladi → yangi parol o'rnatiladi.
Parol tiklangach barcha mavjud refresh_token'lar bekor qilinadi (majburiy re-login barcha qurilmalarda).
3.4 Logout va session management
Logout — joriy refresh_token DB'da revoke qilinadi.
"Barcha qurilmalardan chiqish" — user_id bo'yicha barcha refresh_token'lar revoke qilinadi.
Aktiv sessiyalar ro'yxati (qurilma, IP, oxirgi faollik) Settings > Security bo'limida ko'rsatiladi.
3.5 Xavfsiz token mexanizmi
JWT imzosi: RS256 (asymmetric) — backend private key bilan imzolaydi, boshqa servislar public key bilan tekshiradi.
Refresh token rotatsiyasi: har safar yangilanganda eskisi bekor qilinadi (reuse detection — eski token qayta ishlatilsa, shu userning barcha tokenlari darhol bekor qilinadi, xavfsizlik hodisasi sifatida audit_logs ga yoziladi).

5. Multi-tenant arxitektura
Strategiya: Shared database, shared schema, har bir jadvalda business_id (va kerak bo'lsa branch_id) ustuni + Row-Level Security (RLS, PostgreSQL) orqali majburiy filtr.
Har bir DB ulanishi/so'rov boshida `SET app.current_business_id = '<uuid>'` o'rnatiladi; RLS policy `USING (business_id = current_setting('app.current_business_id')::uuid)` shaklida barcha tenant-scoped jadvallarga qo'llaniladi.
API darajasida ham qo'shimcha himoya: JWT'dagi business_id bilan so'rov path/body'dagi business_id solishtiriladi — mos kelmasa 403.
Bir foydalanuvchi bir nechta biznesga ega bo'lishi mumkin (business_users), lekin bir so'rov faqat bitta tenant kontekstida bajariladi.
Migratsiya/seed skriptlari va background job'lar ham tenant_id kontekstisiz global so'rov yubormasligi kerak (xavfsizlik testida tekshiriladi — 32-bo'lim).

7. POS / Kassa
7.1 Qidiruv
Mahsulot nomi bo'yicha fuzzy search (debounce 300ms, min 2 belgi).
SKU/barcode bo'yicha exact match — barcode skaner qurilmasi HID (klaviatura emulyatsiyasi) orqali ishlaydi, Enter bosilganda avtomatik qidiruv ishga tushadi.
Barcode topilmasa — "Mahsulot topilmadi, qo'shishni xohlaysizmi?" tezkor yaratish modali.
7.2 Savat (cart)
Har bir qatorda: mahsulot, birlik narx, miqdor (+/- va qo'lda kiritish), chegirma (% yoki summa), qator summasi.
Miqdor mahsulot qoldig'idan oshsa — ogohlantirish ko'rsatiladi, lekin sozlamada "minus qoldiqqa ruxsat berish" yoqilgan bo'lsa davom etadi (aks holda bloklanadi).
Umumiy chegirma (butun chekka) va qatorlar chegirmasi birga qo'llanilishi mumkin, lekin hisoblash tartibi: avval qator chegirmalari, keyin umumiy chegirma subtotal ustiga qo'llanadi.
7.3 To'lovlar
Bitta yoki aralash to'lov (masalan 50% naqd + 50% karta) — payments jadvalida bir nechta yozuv.
Aralash to'lovda SUM(payments.amount) === orders.total bo'lishi majburiy, aks holda order 'open' holatida qoladi (qisman to'langan).
Click/Payme integratsiyasi — QR/link generatsiya qilinadi, webhook orqali tasdiqlanadi (V2), muvaffaqiyatsiz bo'lsa order avtomatik bekor qilinmaydi, kassir qo'lda qayta urinadi.
7.4 Tranzaksiya oqimi (state machine)
order (draft) → payment(lar) qo'shiladi → agar to'liq to'langan bo'lsa: inventory kamayadi (inventory_transactions: reason='sale') → revenues yozuvi yaratiladi → order.status='completed' → chek generatsiya qilinadi → dashboard/hisobotlar real-time yangilanadi (WebSocket event: order.completed).
Chegaraviy holatlar
To'lov jarayonida internet uzilsa: order 'draft' holatida local (offline) saqlanadi, inventory kamaytirilmaydi — faqat sync bo'lgach yakunlanadi (31-bo'lim).
Bir vaqtda ikki kassir bitta mahsulotni sotsa (race condition): inventory kamaytirish DB darajasida `SELECT ... FOR UPDATE` yoki atomik `UPDATE ... WHERE quantity >= :qty` orqali himoyalanadi; yetarli bo'lmasa 409 Conflict qaytariladi.
Bekor qilingan (void) order — inventory harakati bo'lmagan bo'lsa shunchaki status='cancelled'; agar inventory allaqachon kamaygan bo'lsa, refund oqimi (16-bo'lim) orqali qaytariladi.
8. Chek
Chek maydonlari: biznes logotipi, biznes nomi, manzil, telefon, order_number, sana/vaqt, kassir ismi, mahsulotlar ro'yxati (nomi, miqdori, narxi, summasi), subtotal, chegirma, soliq, jami (total), qo'llanilgan to'lov usul(lar)i va summalari, qaytim (agar naqd bo'lsa).
Formatlar: 80mm termal printer (ESC/POS orqali, desktop ilovadan to'g'ridan-to'g'ri chop etish), PDF (A4/A5), ekранda ko'rish.
"Qayta chiqarish" (reprint) funksiyasi — audit_logs ga 'reprint' harakati sifatida yoziladi (kim, qachon, necha marta).
Chekda QR-kod (order_id ga link, kelajakda elektron chek tizimi bilan integratsiya uchun zaxira maydon).

10. Inventory / Ombor
Real-time qoldiq — inventory.quantity, har bir order/purchase/transfer tranzaksiyasi bilan atomik yangilanadi (DB transaction ichida).
reserved_qty — checkout jarayonida (to'lov kutilayotganda) mahsulot vaqtincha "band" qilinadi, to'lov muvaffaqiyatsiz bo'lsa yoki 5 daqiqadan keyin avtomatik bo'shatiladi.
available_qty = quantity − reserved_qty — POS ekranida shu ko'rsatiladi.
10.1 Stock In / Stock Out / Transfer
Stock In — sabab: purchase (ta'minotchidan) yoki manual (inventarizatsiya tuzatish). purchase_price yangilanishi ixtiyoriy (weighted average yoki oxirgi narx — sozlamada tanlanadi).
Stock Out — sabab: sale (avtomatik, POS orqali), damage, expired, manual, transfer_out.
Stock Transfer — from_branch dan chiqim (transfer_out) va to_branch ga kirim (transfer_in) ikkita alohida inventory_transactions yozuvi bilan, status='in_transit' bosqichida tovar "yo'lda" hisoblanadi (na jo'natuvchida, na qabul qiluvchida ko'rinmaydi qoldiq sifatida — alohida in_transit_qty da kuzatiladi).
10.2 Tarix
Har bir o'zgarish inventory_transactions jadvalida quantity_before/after bilan saqlanadi — bu yerdan istalgan mahsulotning istalgan vaqtdagi qoldig'ini qayta hisoblash mumkin (audit va nizolarni hal qilish uchun).
11. Suppliers
Supplier maydonlari: name (majburiy), phone, address, company_name, balance (avtomatik hisoblanadi), notes.
Purchase (xarid) yaratilganda: agar to'lov to'liq qilinmasa, farq supplier.balance ga qo'shiladi (biznes qarzdor).
Payment (to'lov) yozuvi supplier balance ni kamaytiradi; balance manfiy bo'lishi mumkin (ortiqcha to'langan holat).
Tarix — barcha purchase va payment yozuvlari xronologik tartibda supplier profilida ko'rinadi.
12. Customers
Maydonlar: full_name (majburiy), phone (ixtiyoriy lekin tavsiya etiladi, UNIQUE per business), birth_date, notes, total_purchases, total_spent, debt, last_purchase_at (oxirgi 4 tasi trigger/job orqali avtomatik yangilanadi, qo'lda tahrirlanmaydi).
Qarz bilan sotish (nasiya) — order to'liq to'lanmasa va mijoz tanlangan bo'lsa, farq customers.debt ga qo'shiladi.
Kelajakda (V2/V3): loyalty ball tizimi, bonus, discount darajalari, customer groups (VIP, doimiy, yangi) — customer_groups va loyalty_points jadvallari qo'shiladi.

14. Finance
Revenue turlari: sales (POS/order orqali avtomatik), services (appointment orqali), other (qo'lda kiritiladigan boshqa daromad).
Expense turlari: product purchase, salary, rent, utilities, advertising, transport, other — har biri category enum orqali belgilanadi va Reports'da kesim (breakdown) sifatida chiqadi.
COGS (Cost of Goods Sold) — sotilgan mahsulotning purchase_price asosida avtomatik hisoblanadi: SUM(order_items.quantity * product.purchase_price snapshot).
Net Profit = Revenue − COGS − Expenses. Bu formula backendda alohida view/materialized query sifatida saqlanadi, frontendda qayta hisoblanmaydi (bitta manba — single source of truth).
Revenue va profit hech qachon bitta ustunda aralashtirilmaydi — Dashboard va Reports'da alohida qatorlar/kartalar sifatida ko'rsatiladi.
14.1 Edge case'lar
Refund bo'lganda — tegishli revenue yozuvi manfiy (reversal) yozuv bilan tuzatiladi, asl yozuv o'chirilmaydi (audit trail saqlanadi).
Valyuta — v1 da faqat business.currency (default UZS), multi-currency V3 uchun zaxira.

16. Refund / Qaytarish
Holat mashinasi (state machine):
1) Kassir yakunlangan order'ni tanlaydi (faqat status='completed' bo'lgan orderlar qaytarish uchun mavjud).
2) Qaytariladigan order_item(lar) va miqdor belgilanadi (qisman yoki to'liq qaytarish, quantity <= order qatoridagi asl miqdor − avval qaytarilgan miqdor).
3) Sabab tanlanadi (majburiy matn maydoni: buzuq, mos kelmadi, mijoz fikri o'zgardi va h.k.).
4) Tasdiqlash — permission refunds.create talab qilinadi; katta summadagi refund (sozlamada belgilangan chegaradan yuqori) Owner/Admin tasdig'ini talab qilishi mumkin (V2, approval flow).
5) refund yozuvi yaratiladi → stock tiklanadi (inventory_transactions: reason='refund', type='in') → revenue reversal yoziladi → order.status='refunded' (to'liq) yoki 'partially_refunded'.
Refund tarixi — har bir order profilida to'liq ko'rinadi (kim, qachon, nima uchun, qancha).
Naqd to'lovda pul qaytarish qo'lda amalga oshiriladi (tizim faqat summani ko'rsatadi); karta/Click/Payme'da avtomatik reversal API chaqiriladi (V2).

17.3 Asosiy oqim (flow)

Order yopilmasdan waiter tizimdan chiqib ketsa — order 'open' holatida boshqa waiter/admin tomonidan davom ettirilishi mumkin (order xodimga emas, stolga bog'liq).
18. Kitchen Display System
Yangi order_item kitchen_orders'ga tushishi bilan real-time (WebSocket) orqali oshxona ekraniga chiqadi, status='new'.
Oshpaz item'ni bosib 'cooking' ga o'tkazadi (started_at belgilanadi), tayyor bo'lgach 'ready' (ready_at belgilanadi).
Waiter ekranida real-time 'ready' bo'lgan item'lar ajratib ko'rsatiladi (ovozli/vizual signal bilan), 'served' deb belgilanganda kitchen ekranidan olib tashlanadi.
SLA kuzatuvi (V2): agar item 15 daqiqadan ortiq 'cooking' holatida qolsa, rangi qizil bo'lib ogohlantiradi.
19. Kafe
Restaurant modulining soddalashtirilgan konfiguratsiyasi: quick_order rejimi yoqiladi (stolsiz, to'g'ridan-to'g'ri POS'ga o'xshash tezkor order).
Takeaway order_type — table_id=NULL, chekda "Olib ketish" belgisi chiqadi.
Stollar soni odatda kam (5–15), menyu qisqartirilgan bo'lishi mumkin, lekin ma'lumotlar strukturasi restaurant bilan bir xil (Core qayta yozilmaydi — 39-bo'lim qoidasi).

27. API
27.1 Umumiy qoidalar
Base URL: /api/v1. Barcha so'rovlar (login/register'dan tashqari) Authorization: Bearer <access_token> talab qiladi.
Barcha ro'yxat (list) endpointlari pagination qo'llab-quvvatlaydi: ?page=1&limit=20 (default limit=20, max=100), javobda meta: { page, limit, total, total_pages }.
Filtrlash: ?filter[status]=active, saralash: ?sort=-created_at (minus = kamayish tartibida).
Barcha yozish (POST/PUT/PATCH/DELETE) so'rovlari tegishli permission bilan himoyalangan (403 agar yo'q bo'lsa) va audit_logs ga yoziladi.

28. Frontend
Tavsiya etilgan stack: Vue 3 (Composition API) + TypeScript + Vite + Pinia + Vue Router + Tailwind CSS.
28.1 Papka arxitekturasi
src/components — qayta ishlatiluvchi UI komponentlar (atomic: base/, forms/, tables/).
src/views — sahifalar (route darajasida).
src/layouts — DefaultLayout (sidebar+header), AuthLayout, POSLayout (soddalashtirilgan, fullscreen).
src/stores — Pinia store'lar (auth, business, cart, inventory, ...).
src/services — API client qatlami (axios/fetch wrapper, har bir modul uchun alohida service fayli).
src/composables — useAuth, usePermission, useDebounce, useRealtime va h.k.
src/utils — formatCurrency, formatDate, validators.
src/types — TypeScript interfeyslar (backend DTO'lariga mos).
28.2 Muhim frontend qoidalari
Sidebar business_type va foydalanuvchi permission'lari asosida dinamik generatsiya qilinadi (statik hardcode qilinmaydi).
usePermission composable — v-if="can('products.create')" kabi direktivalar orqali UI elementlarini yashirish/ko'rsatish uchun ishlatiladi (lekin bu faqat UX — haqiqiy himoya backendda).
Barcha pul qiymatlari formatCurrency orqali business.currency bo'yicha formatlanadi (masalan 45 000 so'm).
Real-time yangilanishlar (yangi order, kitchen status) WebSocket store orqali global holatga tarqatiladi.
29. Backend
Tavsiya etilgan stack: Node.js + NestJS + PostgreSQL + Prisma (yoki TypeORM) + Redis (cache/queue) + JWT + WebSocket (Socket.IO/nestjs/websockets).
29.1 Modul arxitekturasi (NestJS module per domain)
auth, users, businesses, branches, products, inventory, orders, payments, customers, employees, finance, reports, restaurant, appointments, notifications — har biri alohida NestJS module (controller + service + DTO + repository).
Umumiy (shared) qatlam: TenantMiddleware (business_id ni request context'ga joylashtiradi), PermissionGuard (RBAC tekshiruvi), AuditInterceptor (yozish amallarini avtomatik audit_logs ga yozadi).
Redis: sessiya/refresh-token qora ro'yxati, rate-limiting, low-stock job navbati, real-time pub/sub (ko'p instance bo'lganda WebSocket sinxronizatsiyasi uchun).
29.2 Transaction va konsistentlik
Order complete, refund, stock transfer kabi ko'p jadvalga yozadigan amallar — bittalik DB transaction (BEGIN...COMMIT) ichida, xato bo'lsa to'liq rollback.
Optimistic yoki pessimistic locking — inventory yangilanishida `SELECT...FOR UPDATE` (pessimistic) tavsiya etiladi, yuqori parallellikda deadlock oldini olish uchun har doim bir xil tartibda qulflash (masalan product_id bo'yicha ASC).
30. Desktop
Tauri 2 + Vue 3 orqali Windows uchun POS ilovasi — web frontend bilan katta qismi umumiy kod (monorepo, shared UI komponentlar).
Rust backend (src-tauri) — printer (ESC/POS), barcode skaner (HID) va offline local DB (SQLite) bilan to'g'ridan-to'g'ri ishlash uchun.
Ilova: Web App (to'liq boshqaruv) + Desktop POS (tezkor kassa, printer/skaner integratsiyasi) + responsive mobil interfeys (brauzer orqali) — uchtasi bitta backend API bilan ishlaydi.
31. Offline mode
Desktop POS'da SQLite local DB — mahsulotlar, narxlar, mijozlar katalogi periodik (masalan har 10 daqiqada, internet bor bo'lsa) sinxronlanib turadi.
Internet uzilganda: order local DB'ga 'pending_sync' statusi bilan yoziladi, chek local ma'lumot asosida chop etiladi (order_number vaqtinchalik local prefiks bilan, masalan LOCAL-00007).
Internet qaytganda Sync Engine: pending_sync orderlarni server'ga navbat bilan yuboradi, server tomonda order_number qayta generatsiya qilinadi, inventory serverda qayta hisoblanadi (agar shu orada boshqa kanal orqali qoldiq kamaygan bo'lsa — conflict holatida server "yutadi", farq admin uchun reconciliation ro'yxatida ko'rsatiladi).
Offline rejim MVP'dan keyingi bosqichda (V3) to'liq ishlab chiqiladi; MVP'da faqat internet uzilishini aniqlash va foydalanuvchini ogohlantirish yetarli.

37. UI/UX talablari
Uslub: modern, minimal, professional — soft rounded cards, generous whitespace, niche'ga mos (masalan restoran uchun issiq, sartaroshxona uchun neytral) pastel/gradient palitra.
Dark/Light mode — tizim sozlamasini avtomatik aniqlash + qo'lda almashtirish, tanlov localStorage/user preference'da saqlanadi.
Responsive: desktop-first, lekin tablet (POS uchun muhim) va mobile to'liq qo'llab-quvvatlanadi (breakpoint: 640/768/1024/1280px).
Sidebar — business_type'ga qarab faqat tegishli modullarni ko'rsatadi (masalan sartaroshxonada 'Kitchen' bo'limi umuman ko'rinmaydi).
Statistik ma'lumotlar uchun progress ring/gauge komponentlar linear bar'dan afzal ko'riladi (Dashboard KPI kartalarida).
38. Asosiy user flow
Do'kon
Login → Business → Dashboard → POS → Scan Product → Cart → Payment → Receipt → Inventory Update → Finance Update.
Restoran
Login → Restaurant → Table → Order → Kitchen → Prepare → Serve → Payment → Close Table.
Sartaroshxona
Customer → Appointment → Barber → Service → Completed → Payment → Receipt.
Har bir flow'dagi har bir qadamda muvaffaqiyatsizlik holati (masalan to'lov rad etilishi, mahsulot yetishmasligi) uchun aniq xato xabari va qaytish yo'li (retry/cancel) UI darajasida ta'minlanishi shart.
39. Asosiy arxitektura qoidasi
Restaurant POS va Shop POS alohida dastur sifatida qurilmaydi — bitta POS komponenti order_type parametriga qarab moslashadi.
UBMS Core (Auth, Business, Branch, Users, RBAC, Notifications, Audit) umumiy; POS, Inventory, Finance — umumiy qatlamlar (barcha biznes turlarida ishlatiladi); Shop, Restaurant, Salon — biznes-modullari (feature flag orqali yoqiladigan, Core'ga bog'liq lekin Core ularga bog'liq emas — bir tomonlama bog'liqlik).
Yangi biznes turi qo'shilganda: yangi feature-module yoziladi + business_type_modules konfiguratsiyasiga qator qo'shiladi; Core kod (auth, RBAC, POS asosiy engine, inventory engine) o'zgartirilmaydi.
